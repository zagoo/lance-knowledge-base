4: //! Inner-product kernels between an `f32` query and bit-packed RaBitQ ex-codes.
5: //!
6: //! Multi-bit RaBitQ reranking reduces to `sum_d query[d] * ex_code[d]`, where
7: //! `ex_code[d]` is an unsigned `ex_bits`-wide integer. Materializing a
8: //! `dim * 2^ex_bits` lookup table and gathering one entry per dimension is
9: //! cache-hostile (the table is 1MiB for `ex_bits=8`, `dim=1024`); these kernels
10: //! instead unpack the codes with shifts and masks and FMA them against the
11: //! query directly, following the kernel design of the RaBitQ reference library
12: //! (<https://github.com/VectorDB-NTU/RaBitQ-Library>, Apache-2.0).
13: //!
14: //! Codes are stored in the *blocked* layout: dims are grouped into 64-dim
15: //! blocks (the last block zero-padded) and bit-interleaved within each block
16: //! so that the SIMD unpack emits codes in natural dim order:
17: //!
18: //! ```text
19: //! per 64-dim block (T = ex_bits - 1, the top bit; "run k" = dims 16k..16k+16):
20: //! 1 bit:  [8B]  bit i of the LE word = dim i
21: //! 2 bits: [16B] byte b = dims {b, b+16, b+32, b+48} at bit pairs 0/2/4/6
22: //! 3 bits: [16B 2-bit plane as above][8B top-bit plane]
23: //! 4 bits: [32B] byte 8j+b = dim 16j+b (low nibble) | dim 16j+8+b (high nibble)
24: //! 5 bits: [32B 4-bit plane: byte b = dims b|b+16; byte 16+b = dims b+32|b+48]
25: //!         [8B top-bit plane]
26: //! 6 bits: [48B] byte 16k+b = dim 16k+b (6 low bits) | bits 2k..2k+2 of
27: //!         dim 48+b (2 high bits)
28: //! 7 bits: [48B as 6 bits][8B top-bit plane]
29: //! 8 bits: [64B] identity
30: //! top-bit plane: top bit of dim 16k+b at bit 8*(b%8) + 2k + b/8 of a LE u64
31: //! ```
32: //!
33: //! Because unpack order is natural, the kernels read the rotated query
34: //! directly; it only needs zero-padding ([`pad_query_into`]) when the rotated
35: //! dim is not a multiple of 64. Legacy indexes store ex codes sequentially
36: //! (LSB-first bit stream) and are repacked once at load time
37: //! ([`repack_sequential_row`]); for `ex_bits` ∈ {1, 8} the two layouts agree
38: //! (modulo trailing padding, which the kernels tolerate) and rows are used as

6: //! JSONB encoding for Lance JSON columns.
7: //!
8: //! Lance stores `lance.json` columns as JSONB values in `LargeBinary` arrays.
9: //! This crate owns that encoding: it parses JSON text into JSONB
10: //! ([`parse_value`], [`OwnedJsonb`]), reads JSONB values ([`RawJsonb`],
11: //! [`from_raw_jsonb`]), and evaluates SQL/JSONPath expressions over them
12: //! ([`jsonpath`]).
13: //!
14: //! ```
15: //! use lance_jsonb::OwnedJsonb;
16: //! use lance_jsonb::jsonpath::{Selector, parse_json_path};
17: //!
18: //! let jsonb: OwnedJsonb = r#"{"user":{"name":"Ada","tags":["a","b"]}}"#.parse().unwrap();
19: //! let path = parse_json_path(b"$.user.tags[1]").unwrap();
20: //! let value = Selector::new(jsonb.as_raw()).select_value(&path).unwrap().unwrap();
21: //! assert_eq!(value.to_string(), r#""b""#);
22: //! ```
23: //!
24: //! The implementation is adapted from
25: //! [databendlabs/jsonb](https://github.com/databendlabs/jsonb) and keeps only
26: //! what Lance uses. See the crate README for the upstream revision and the
27: //! differences from it.
28: //!
29: //! ## Compatibility
30: //!
31: //! The byte layout below is persisted in Lance data files. Every change must
32: //! keep reading values written by released Lance versions, and writers must keep
33: //! producing bytes that those versions can read. `tests/it/compat.rs` pins the
34: //! bytes produced for representative inputs.
35: //!
36: //! ## Encoding format
37: //!
38: //! The JSONB encoding format is a tree-like structure. Each node contains a container header, a number of JEntry headers, and nested encoding values.
39: //!
40: //! - 32-bit container header. 3 bits identify the type of value, including `scalar`, `object` and `array`, and 29 bits identify the number of JEntries in the `array` or `object`. The root node of the `jsonb` value is always a container header.

FILE rust/lance/src/dataset/mem_wal/index/arena_skiplist.rs
4: //! Single-writer, lock-free-read skiplist with no epoch reclamation.
5: //!
6: //! Purpose-built for the MemTable scalar index, whose access pattern is:
7: //! append-only (no per-entry delete), a single writer (serialized by the
8: //! `ShardWriter` actor), and many concurrent readers. Under that pattern there
9: //! is nothing to reclaim until the whole index is dropped, so — unlike a
10: //! general-purpose concurrent skiplist (`crossbeam_skiplist`) — we pay **no
11: //! epoch pin** on reads. Profiling showed crossbeam's per-operation epoch
12: //! pinning (`try_pin_loop`) dominating the point-lookup hot path and, worse,
13: //! contending across threads (the N-thread read-scaling bottleneck). This
14: //! mirrors RocksDB's arena `InlineSkipList`: nodes live for the index's whole
15: //! life, readers only do `Acquire` loads, the writer publishes with `Release`.
16: //!
17: //! # Node layout (cache locality)
18: //! The seek is **cache-miss bound** — each tower hop loads a node's key. So a
19: //! node is a **single bump-arena allocation** with the key and its forward-
20: //! pointer tower laid out contiguously (`[key][AtomicPtr; height]`), exactly
21: //! like RocksDB. This is one cache miss per hop, not two (a separate boxed
22: //! tower measured ~2x slower single-thread). Nodes are bump-allocated from
23: //! large chunks, so they are also contiguous in insertion order.
24: //!
25: //! # Safety model
26: //! - **Single writer.** Only [`SkipListWriter`] mutates (the sole `&mut`).
27: //!   Callers must serialize writes (the MemTable does so via the actor; the
28: //!   BTree index additionally guards the writer behind a `Mutex`).
29: //! - **No free before drop.** Nodes live in the arena and are freed only when
30: //!   the core (the whole index generation) drops, when no readers remain. So a
31: //!   reader can never observe a freed node. Node addresses are stable (bump
32: //!   chunks never move or realloc).
33: //! - **Publish/consume.** The writer initializes a node fully, then links it in
34: //!   with `Release` stores; readers follow links with `Acquire` loads, so a
35: //!   reader that sees a pointer also sees the fully-initialized node.
36: //! - **In-bounds towers.** A node is linked at level `L` only if its height is
37: //!   `> L`, so any node reached during a level-`L` traversal has a tower slot at
38: //!   `L` — reads never run off the end of a variable-length tower.

4: //! Full-text search planner for LSM scanner (local scoring).
5: //!
6: //! Builds an execution plan that scores an FTS query across the base
7: //! table, SSTable generations, and the active/frozen-undrained
8: //! in-memory memtables, returning rows ordered by BM25 `_score` DESC.
9: //!
10: //! # Scoring
11: //!
12: //! Each source scores with its own corpus statistics (local BM25), and
13: //! the coordinator unions the per-source plans and merges by `_score`
14: //! (per-partition top-k sort + sort-preserving merge). The plan is
15: //! single-pass and never coordinates statistics across sources, so
16: //! cross-source `_score` values are only approximately comparable — but
17: //! within each source the ranking is exact. This mirrors the default
18: //! `query_then_fetch` trade-off of distributed search systems.
19: //!
20: //! A globally-consistent scoring mode (aggregate corpus statistics
21: //! across sources, then rescore) is a deliberate follow-up: the
22: //! benchmark in this PR shows it carries a real latency penalty, so the
23: //! local path lands first and the global option is optimized separately.
24: //!
25: //! Staleness: within an SSTable, the deletion vector written
26: //! at flush time (see #6929) already masks rows superseded by a newer
27: //! generation, so per-source results are clean within each tier. The
28: //! same primary key can still appear across tiers (active vs SSTable)
29: //! when an updated row sits in the active memtable while the older
30: //! copy lives in an SSTable; cross-tier deduplication is
31: //! left to the caller in local mode.
32: //!
33: //! Everything here is contained in the `mem_wal` module — it reuses the
34: //! existing per-source FTS read paths (`scanner.full_text_search` for
35: //! base/SSTable Lance datasets, `MemTableScanner` for the active
36: //! memtable) and requires no changes to `lance-index`.

4: //! Centroid-based selection of the initial IVF probe budget.
5: //!
6: //! Auto probing is an empirical heuristic, not a recall guarantee. The initial
7: //! budget does not limit subsequent probing when filters leave fewer than k rows.
8: //! `LANCE_AUTO_PROBE_MARGIN` overrides the nonnegative relative distance margin;
9: //! `LANCE_AUTO_MIN_INITIAL_NPROBES` and `LANCE_AUTO_MAX_INITIAL_NPROBES` override
10: //! the positive learned floor and cap. Each override replaces only that profile
11: //! field; the resulting floor must not exceed the resulting cap. Override both
12: //! bounds when an individual change would conflict with the other profile bound.
13: //! The caller minimum takes precedence over the learned cap, while the caller
14: //! maximum and available candidate count limit the final initial budget.
15: //! Explicit fixed nprobes bypasses both the heuristic and these overrides.
16: //! Queries using L2, cosine, or dot with k <= 100000 use these profiles across IVF
17: //! index types, vector types, and refinement factors. The policy selects partitions
18: //! from centroid distances independently of query values, quantization, or the
19: //! search within each partition.
20: //! Explicit maximum bounds limit adaptive probing without disabling it.
21: //! Larger k and Hamming retain their existing heuristic and ignore these overrides.
22: //! Dot uses the magnitude of the best centroid inner product to scale its gap,
23: //! rather than the signed `1 - dot` distance. Corpus and query norms are preserved.
24: //! No extra index statistics or file-format changes are needed.
